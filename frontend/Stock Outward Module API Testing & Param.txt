Stock Outward Module API Testing & Parameters Document


This document provides the exact URL endpoints, request headers, and multi-item dynamic grid payload examples including frontend-calculated values (purity, waste_value / wValue) and custom timestamps (added_at) for testing all modules.

Before testing, run the database seeder to initialize the test users and items in your database:

bash

php artisan db:seed --class=StockTestDataSeeder
Head Admin (User ID 1): Has 1000.0000 grams gold balance, 920.0000 purity balance, and 50,000.0000 cash balance.
Employee Worker (User ID 2): Has 0.0000 gold balance and 1,000.0000 cash balance.
Gold Ring (Item ID 1) and Gold Chain (Item ID 2) are initialized with active mappings.



1. New Out (Stock Outward Entry) - Submitting Multiple Items


Registers multiple outward gold transfers to a worker or retailer in a single API request, including frontend-calculated wastage and purity override values.

URL: POST /api/v1/stock/out

Headers:

Content-Type: application/json
X-User-ID: 1
Request Body (Multiple Rows with 10 fields):

json

{
    "given_by": 1,
    "given_to": 2,
    "items": [
        {
            "item_id": 1,
            "grams": 50.0000,
            "touch": 92.0000,
            "waste_id": 1,
            "waste_total": 0.1800,
            "waste_value": 0.0900,
            "purity": 46.0900,
            "remarks": "Order description 1",
            "item_remarks": "First item remarks",
            "added_at": "2026-08-03 23:26:41"
        },
        {
            "item_id": 2,
            "grams": 30.0000,
            "touch": 92.0000,
            "waste_id": null,
            "waste_total": 0.0000,
            "waste_value": 0.0000,
            "purity": 27.6000,
            "remarks": "Order description 2",
            "item_remarks": "Second item remarks",
            "added_at": "2026-08-03 23:26:41"
        }
    ]m
}





Parameters Description:

given_by (integer): ID of head administrator sending the gold.
given_to (integer): ID of employee receiving the gold.
items (array): List of items to outsource (each item can contain up to 10 fields):
item_id (integer): Reference to the item master.
grams (decimal): Gross weight of gold transferred.
touch (decimal): Touch/purity percentage (e.g. 91.6000).
waste_id (integer, optional): Wastage configuration row ID.
waste_total (decimal, optional): Wastage rate percentage.
waste_value or wValue (decimal, optional): Pre-calculated wastage grams from frontend.
purity (decimal, optional): Pre-calculated purity grams from frontend.
remarks (string, optional): Drop-down selection description.
item_remarks (string, optional): Custom description text.
added_at (string, optional): ISO/Y-m-d H:i:s custom timestamp.

Headers:
Content-Type: application/json
X-User-ID: 1

json

{
    "given_by": 2,

    "amount": 250.0000,

{

    "given_to": 1,
    "amount": 1000.0000,
    "souce_type": "BANK",
    "bank_id": 1,
    "bank_name": "HDFC Bank Ltd",

given_by (integer): ID of sender.

7. Cash To Gold (CUSTOMER Cash receipt for Gold OUT)
Submits a Cash To Gold transaction. Frontend is responsible for calculating standard fields (total_grams, purity). The backend atomically records the transaction, populates payment sources (supporting multiple dynamic rows of CASH or BANK), and records ledger details and stock updates.

URL: POST /api/v1/cash-to-gold
Headers:
Content-Type: application/json
Authorization: Bearer <token> (or fallback user ID)
Request Body (Single Cash Source):
json

{
    "head_id": 1,
    "customer_id": 2,
    "total_cash": 50000.00,
    "per_gram_cash": 6500.00,
    "total_grams": 7.6923,
    "touch": 100.00,
    "purity": 7.6923,
    "item_id": 1,
    "amnt_transfer_to_head": true,
    "remarks": "Gold ring conversion test",
    "amount_sources": [
        {
            "source": "CASH_ON_HAND",
            "bank_id": null,
            "amount": 50000.00
        }
    ]
}
Request Body (Multiple Mixed Sources):
json

{
    "head_id": 1,
    "customer_id": 2,
    "total_cash": 100000.00,
    "per_gram_cash": 6500.00,
    "total_grams": 15.3846,
    "touch": 100.00,
    "purity": 15.3846,
    "item_id": 1,
    "amnt_transfer_to_head": true,
    "remarks": "Split cash and bank sources",
    "amount_sources": [
        {
            "source": "CASH_ON_HAND",
            "bank_id": null,
            "amount": 40000.00
        },
        {
            "source": "BANK",
            "bank_id": 1,
            "amount": 60000.00
        }
    ]
}
Parameters Description:
head_id (integer): ID of head user receiving payment.
customer_id (integer): ID of customer making payment.
total_cash (decimal): Total transaction value.
per_gram_cash (decimal): Gold rate per gram.
total_grams (decimal): Total gold grams weight.
touch (decimal): Touch/purity percentage (defaults to 100).
purity (decimal): Purity value.
item_id (integer): Linked gold item ID.
amnt_transfer_to_head (boolean): Master toggle for Cash/Bank processing (The "Yes/No" Button).
If true (YES): The system processes the amount_sources array. It handles the physical cash movement directly from/to the Head Admin's live Cash/Bank balances and creates CashTxnDetail audit logs. The Customer's cash balance is untouched.
If false (NO): The system completely bypasses the amount_sources array and the Head Admin's balances. Instead, the full cash value is deducted/added directly to the Customer's internal Cash Ledger balance as a Journal Entry.
images (array of files, optional): Receipt image uploads (must be JPG, JPEG, PNG, or WEBP formats up to 5MB each).
amount_sources (array): Breakdown of source rows:
source (string): CASH_ON_HAND or BANK.
bank_id (integer, required if source is BANK): Reference bank ID.
amount (decimal): Split amount for the source row.
8. Gold To Cash (Customer returns Gold for Cash payout)
Submits a Gold To Cash transaction. Frontend calculations are passed directly to backend to insert values into the database atomically.

URL: POST /api/v1/gold-to-cash
Headers:
Content-Type: application/json
Authorization: Bearer <token>
Request Body Example:
json

{
    "head_id": 1,
    "customer_id": 2,
    "total_gold": 7.6923,
    "touch": 100.00,
    "total_grams": 7.6923,
    "per_gram_cash": 6500.00,
    "total_cash": 50000.00,
    "remarks": "Return test",
    "amount_sources": [
        {
            "source": "CASH_ON_HAND",
            "bank_id": null,
            "amount": 50000.00
        }
    ]
}
Parameters Description:
head_id (integer): ID of head user paying out cash.
customer_id (integer): ID of customer receiving cash and returning gold.
total_gold (decimal): Pure weight of gold returned (stored in purity database column).
touch (decimal): Touch percentage.
total_grams (decimal): Adjusted gross weight of gold returned (stored in total_grams database column).
per_gram_cash (decimal): Gold rate per gram.
total_cash (decimal): Total payout amount paid by head.
images (array of files, optional): Receipt image uploads (must be JPG, JPEG, PNG, or WEBP formats up to 5MB each).
amount_sources (array): Breakdown of source rows:
source (string): CASH_ON_HAND or BANK.
bank_id (integer, required if source is BANK): Reference bank ID.
amount (decimal): Payout split amount.

11. Cash Categories Master (CRUD)
Manages the categories used for categorizing cash transactions (Income, Expense, Auto Entry). Supports pagination and soft deletes.

GET /api/v1/cash-categories
Fetches paginated cash categories.
Query Params: limit (default 50).
POST /api/v1/cash-categories
Creates a new category.
Body: {"category_name": "Food", "category_type": "EXPENSE", "is_active": true}
PUT /api/v1/cash-categories/{id}
Updates a category.
Body: {"category_name": "Office Supplies"}
DELETE /api/v1/cash-categories/{id}
Soft deletes a category.

Backend Updates & Redis Setup (For Frontend Developer)
Hey! We just implemented high-performance Redis Cache Tagging for the Cash Dashboard History APIs on the backend. When you pull the latest code, you need to do a couple of quick things to get your local environment working:

1. Pull & Install Dependencies Because we added a new Redis package, make sure you run:

bash
git pull origin Backend
composer install



2. Handle the Redis Cache (Choose Option A or B) Because the backend now actively tries to connect to a Redis server on port 6379, your local API calls will crash with a "target machine actively refused it" error if you don't have Redis running.

Option A: Bypass Redis (Fastest Setup) If you don't want to bother installing Redis on your local computer, you can just tell Laravel to fall back to standard file caching locally.

Open your .env file.
Change CACHE_STORE=redis to CACHE_STORE=file.
Run php artisan config:clear in your terminal.
Option B: Run Redis Locally (To accurately test caching) If you want to experience the actual cache speeds and invalidations:

Download this lightweight Windows Redis zip: Redis-x64-5.0.14.1.zip
Extract the folder anywhere on your PC.
Double-click redis-server.exe to start the server in the background. As long as that black terminal window is open, the APIs will connect to it perfectly!

Vue.js must provide empty input boxes (v-model) for dynamic fields like "Taken" or "Wastage".
Vue.js must dynamically compute the row totals (e.g., (Row Grams) - (Row Taken)) and the global footer sum totals natively in the browser as the user types.
When the user clicks "Save", Vue.js will send the fully computed array payload to the final submission endpoint (e.g., POST /api/v1/gms-out).

Changes & Database Migration (Consolidated Report Optimization)
This API underwent a massive optimization to safely process large datasets (100K+ records) while perfectly retaining legacy business logic parity. Below are the documented architectural changes.

1. Why the changes were required
Scalability and Memory Exhaustion: The previous implementation calculated summary totals by pulling entire filtered recordsets into PHP memory (->get()). During tests with 100K+ rows, hydrating tens of thousands of active Eloquent models instantly exhausted PHP memory constraints, causing fatal API crashes.
Missing Schema Parity: Legacy logic executed math using Auto Entry columns (e.g., to_touch) which physically did not exist in the Laravel database schema, resulting in silent calculation failures or SQL column does not exist errors.
Sequential Scans: Without proper indexing on time-series queries, the database was forced to execute full table scans (Seq Scan) which exponentially slowed down date-range filtering.

2. Database Migration Changes
A new migration (2026_08_28_203540_add_auto_entry_touch_columns_to_stock_details_table.php) was executed to fix schema parity and indexing:

Added Auto Entry Columns:
to_touch, to_mtouch, to_waste_value, to_waste_id, to_waste_total, to_purity (All defined as DECIMAL(12, 4) and INT).
Why:. The AutoEntryService directly requires these to insert transfers, and the Consolidated Report requires them to calculate summary parity.
Added Index: idx_stock_added_at on the added_at column.
Why: Proved by EXPLAIN ANALYZE, date-range queries heavily bottlenecked the API. Introducing this B-Tree index reduced worst-case execution time from 88.47 ms down to 0.195 ms by allowing PostgreSQL to seek directly to the date partition.
3. Removed / Changed Logic
Removed: PHP-level iteration loop over Eloquent Collection.
Why: Passing 74,000 active rows into PHP crashed the server memory.
Replaced With: A raw SQL selectRaw aggregation query executed purely at the PostgreSQL layer.
Removed (Attempted): The toBase()->cursor() PHP Generator pattern was initially tested.
Why: While it kept memory flat, database-level aggregation proved to be exponentially faster and safer for pure mathematical summations.
4. ReportService Changes
The ReportService::calculateTotals() logic was heavily refactored:

The Change: Replaced PHP foreach ($records) summation with PostgreSQL SUM() and CASE WHEN aggregation.
Legacy Parity: The complex nested IF condition (if to_touch > 0 AND entry_type IN ('EMPTOEMP'...) THEN use to_purity) was successfully translated into native CASE WHEN SQL syntax.
Impact: The database engine now mathematically crunches 100,000 rows natively and simply returns 3 integers (total grams, purity, wastage) to Laravel.
5. Pagination and Performance
Deterministic Pagination: Records are paginated using ->orderBy('stock_id', 'desc')->skip(...)->take(...). Because stock_id is the primary key, row ordering is strictly guaranteed and records will never accidentally shift between pages.
100K-Record Benchmark Metrics:

 API Integration & Testing Documentation

This document explains how to integrate and test the Schain ERP APIs, specifically focusing on the Authentication flow and protected routes for frontend development.

## 1. Backend Initial Setup (For Developers)

If you are a developer setting up this project for the first time, you need to ensure the Passport API is fully installed and configured in your local environment.

1. Install Composer dependencies:
   ```bash
   composer install
   ```
2. Run all database migrations (this will create all the necessary Passport tables like `oauth_clients`, `oauth_access_tokens`, etc.):
   ```bash
   php artisan migrate
   ```
3. Generate the Passport encryption keys and create the "Personal Access Client":
   ```bash
   php artisan passport:install
   ```
   *(If prompted "Which user provider should this client use to retrieve users?", just hit Enter to use the default `users` provider).*

## 2. Running the Project Locally

Before making API requests, ensure the Laravel backend server is running on your local machine.

1. Open your terminal in the backend project directory.
2. Run the following command:
   ```bash
   php artisan serve
   ```
3. The API will now be available at `http://localhost:8000/api/v1/...` or `http://127.0.0.1:8000/api/v1/...`

## 3. Essential Frontend Setup

When making requests from the frontend (using fetch, Axios, etc.), you **must** include the following headers in **all** your API requests to ensure Laravel responds correctly:

```javascript
const headers = {
    "Accept": "application/json",
    "Content-Type": "application/json"
};
```
*Note: The `Accept: application/json` header is critical. Without it, Laravel will try to redirect unauthenticated users to a web login page instead of returning a `401 Unauthorized` JSON response.*

## 4. The Authentication Workflow (JWT)

Our backend uses **Laravel Passport** to issue JWT (JSON Web Tokens).

32. Logging In
Send a `POST` request to `/api/v1/login` with the user's credentials:

**Request Body:**
```json
{
    "user_name": "your_username",
    "password": "your_password"
}
```

**Success Response:**
```json
{
    "success": true,
    "message": "Login successful",
    "data": {
        "user": { ... },
        "token": "eyJ0eXAiOiJKV1QiLCJhb...",
        "token_type": "Bearer"
    }
}
```

### 2. Accessing Protected Routes
Extract the `token` from the login response and store it securely (e.g., in memory or secure storage). For all subsequent requests to protected routes, include it in the `Authorization` header:

```javascript
headers["Authorization"] = `Bearer ${your_extracted_token}`;
```

## 5. Testing via Postman

We have prepared a ready-to-use Postman Collection (`Schain_ERP_Postman_Collection.json`) in the root directory.

1. **Import the Collection:** Open Postman -> Import -> Select the JSON file.
2. **Automated Tokens:** Open the `Authentication > Login` request and send it. Postman will automatically extract the JWT token from the response and save it to a variable `{{auth_token}}`.
3. **Test Protected Routes:** Open any other route. The Authorization tab is already configured to use the Bearer `{{auth_token}}`, so you can just click Send!

| `All other /api/v1/*` | `...` | `auth:api` | Requires `Authorization: Bearer <token>` |
